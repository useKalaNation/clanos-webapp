# CLANOS: rules for every coding agent

These rules apply to every task in this repo, whichever agent or person does the work. If a prompt conflicts with them, follow these rules and say so.

## 1. Design tokens are the only source of visual values

`src/styles/tokens.css` holds every colour, font, type size, space, radius and layout size in the product. It's generated by the CLANOS design package, so **never edit it by hand**. `_docs/design/tokens.json` holds the same values in DTCG format.

- **Use tokens** through CSS variables (`var(--s1)`, `font: var(--t-h2)`) or the Tailwind utilities mapped from them in `src/app/globals.css`.
- **Never write raw visual values** in components or styles:
  - no hex, `rgb()`, `hsl()` or `oklch()` colours
  - no font names, and no px font sizes, line heights or letter spacing
  - no px spacing or radius values
  - no Tailwind arbitrary values such as `bg-[#17191f]`, `text-[15px]`, `p-[13px]` or `rounded-[10px]`
  - no inline `style={{ … }}` with literal colours or sizes
- **Allowed literals:** `0`, 1–2px border and outline widths (with token colours), percentages, `fr`, `auto`, z-index, and animation durations.
- **A value isn't a token?** Don't invent one. Use the closest token, add `/* TODO(token): <what's missing> */`, and mention it in your summary. New tokens are added in the design package (`tools/tokens.py`), never directly in `tokens.css`.
- Tailwind's default palette, font sizes and radii are switched off on purpose. Don't re-enable them.

## 3. Desktop and mobile

- Layout and type tokens switch automatically below **768px**. Colours, space and radius never change.
- Build mobile-first. Base styles are the mobile design (M frames, 390px); `md:` is the desktop design (D frames, 1440px). Tailwind's `md` breakpoint is also 768px, so it lines up with the tokens. Don't add other breakpoints.
- Below 768px: tab bar + drawer instead of the sidebar, cards instead of tables, bottom sheets instead of dialogs, and action bars fixed at the bottom.
- Every tappable element is at least `var(--control-touch-target)` (44px). Inputs use `--t-input` (16px on mobile, which stops iOS zooming in).

## 4. Match the designs

- `_docs/design/HANDOFF.md` has the screen inventory, routes, roles, component names and open decisions. The Figma file is linked from `_docs/design/README.md`.
- The Figma file has every frame, named like `D26 · Clan dashboard / Clan Master` and `M26 · …`: D is desktop (1440px), M is mobile (390px). **The same number is the same screen.** Compare your result with both before finishing.
- Status always pairs a glyph with a colour (● ◐ ▲ ○ ✓ ✕ ⏳ ⊘), never colour alone.
- Use the component names from HANDOFF.md (ClanHeader, MemberTable / MemberCard, InvitationTable, InviteDialog, RecruitmentQueue, RoleEditor, AnnouncementComposer, …).

## 5. Stack and architecture

| Concern | Use | Rule |
|---|---|---|
| Language | TypeScript, `strict` + `noUncheckedIndexedAccess` | No `any`. Use `unknown` and narrow it. |
| Framework | Next.js App Router | Server Components by default. Add `"use client"` only where interactivity needs it. |
| UI primitives | shadcn/ui in `src/components/ui` | Adapted to the tokens. Never use shadcn's default theme values. |
| Forms | React Hook Form + Zod (`zodResolver`) through shadcn `Field` (`Controller` + `Field`, `FieldLabel`, `FieldError`) | One Zod schema per form in the feature's `schemas/`, reused for server-side validation. shadcn has retired its old `Form` component. |
| HTTP | axios, **only** through `src/lib/api/client.ts` | Components and hooks never import axios directly (ESLint enforces this). |
| Server state | TanStack Query | Query and mutation hooks live in `features/<x>/api/`. Never copy server data into Zustand or Context. |
| Client state | Zustand, one small store per concern | Only for UI state shared by distant components (drawer open, active clan). Local state stays in `useState`. |
| Context | Providers only | QueryClientProvider, session, toasts. Not for state that changes often. |
| URL state | Search params | Filters, tabs and pagination (e.g. `?tab=invitations`), so every view can be shared and reloaded. |
| Environment | `process.env`, documented in `.env.example` | Every variable is listed in `.env.example` with what it's for. Read it where it's needed, with a safe default or explicit handling when it's missing. |
| Tests | Vitest + React Testing Library + MSW; Playwright for end-to-end | Test behaviour, not implementation. |
| Component docs | Storybook (`@storybook/nextjs-vite`) with autodocs and the a11y addon | Every component has a story. Stories also run as Vitest browser tests, so an a11y violation fails CI. |

**Every component ships with a story and a test.** Each `.tsx` file in `src/components/**` and `src/features/*/components/**` has a sibling `<name>.stories.tsx` (one story per variant and state) and `<name>.test.tsx` (its behaviour). `pnpm check:stories` enforces this.

```text
_docs/                  architecture, ADRs, design reference (HANDOFF, tokens.json, Figma link), guides
src/
  app/                  routes only: (public), (auth), (app) route groups; pages stay thin
  components/ui/        shadcn primitives, token-adapted; each with .stories.tsx and .test.tsx
  components/layout/    AppShell, Sidebar, TopBar, TabBar, Drawer, BottomSheet
  features/<feature>/   auth, clans, members, recruitment, announcements, teams, rules, settings, profile, admin
    api/                axios calls + TanStack Query hooks
    components/         the feature's UI
    schemas/            Zod schemas for forms and API responses
    store.ts            Zustand store, only if the feature needs one
    index.ts            the feature's public API; other code imports only from here
  lib/                  api client, query client, utils, security helpers
  styles/tokens.css     generated; never edit
  proxy.ts              security headers (and the sign-in redirect, once API auth is wired)
  test/                 test setup, MSW handlers and fixtures
```

- Import with `@/…`. A feature never reaches into another feature's folders, only its `index.ts` (ESLint enforces this). Inside a feature, use relative imports.
- One component per file. shadcn primitives in `components/ui` are the exception: a compound component (`Dialog`, `DialogContent`, …) stays in one file. File names in kebab-case, components in PascalCase, hooks start with `use`.
- No magic numbers or strings: use tokens, constants or enums.

## 6. Code style and comments

- ESLint and Prettier are the authority. Don't disable them; when a disable is truly needed, write `// eslint-disable-next-line <rule> -- <reason>`.
- **Comments explain why, not what.** Keep each comment to **3 lines or fewer**. If you need more, the code should be simpler, or the reasoning belongs in the PR description or an ADR in `_docs/adr/`.
- Brief JSDoc is welcome on exported functions, hooks and components: purpose, parameters, gotchas.
- No commented-out code. No `TODO` without an issue number: `TODO(#123): …`.
- Prefer early returns, small functions and descriptive names over clever code.

## 7. Security (non-negotiable)

- **Secrets:** never commit them. Server-only values have no `NEXT_PUBLIC_` prefix and are read only in server code; a module that reads one starts with `import 'server-only'` (add the package the first time), so importing it from the client fails the build. Only `.env.example` is committed.
- **Sessions:** auth uses httpOnly, Secure, SameSite cookies set by the API. Never store tokens in localStorage, sessionStorage, Zustand or Context.
- **Validation:** validate every input with Zod on the client **and** on the server (route handlers, server actions). Hiding a button is not authorization; the API is the authority.
- **Permissions:** every server action and route handler checks the session and the specific permission (for example `members.suspend`) before doing anything.
- **XSS:** no `dangerouslySetInnerHTML`. If rich text is ever needed, sanitize it on the server.
- **Links and images:** links with `target="_blank"` get `rel="noopener noreferrer"`. Images load only from the allowed `remotePatterns`.
- **Headers:** CSP (with nonces), HSTS, `X-Content-Type-Options`, `Referrer-Policy`, `Permissions-Policy` and `frame-ancestors 'none'` are set centrally. A feature PR never weakens them.
- **Errors and logs:** errors shown to users never include stack traces, tokens or other people's data. Never log passwords, tokens, cookies or full email addresses.
- **Privacy:** never reveal whether an email is registered (sign-in errors, forgot password, invitations), as the designs specify.
- **Uploads:** check type and size on the client for UX; the server re-validates.
- **Dependencies:** a new dependency needs a reason in the PR description. Prefer well-maintained packages, and don't add one for something a few lines can do.

## 8. Git workflow

- **Never commit or push to `main` or `dev`.** All work happens on a branch and lands through a pull request.
- **`dev` is the integration branch.** Every feature, fix and chore PR targets `dev` (`gh pr create --base dev`) and is squash-merged. `main` only receives release PRs from `dev`, merged with a merge commit so the two branches never diverge.
- **Branch names:** `<type>/<short-description>`, optionally with the issue number, e.g. `feat/clan-directory`, `fix/123-invite-expiry`, `chore/update-deps`. Types: `feat`, `fix`, `chore`, `docs`, `refactor`, `perf`, `test`, `build`, `ci`, `style`, `revert`.
- **Commits** follow Conventional Commits, with the feature folder as the scope: `feat(clans): add directory filters`.
- **Pull requests:** open them with `gh pr create`.
  - The title is a Conventional Commit; it becomes the squash-merge commit.
  - The body fills in every section of `.github/pull_request_template.md`: what and why, type, screens (D##/M##), how to test, desktop and mobile screenshots, security notes, checklist.
- Keep PRs small and about one thing. Never use `--no-verify`, never force-push a shared branch, never merge your own PR. Coding agents never use the admin bypass (ADR 0005); it's for people, when no reviewer is available.

## 9. Documentation is part of the change

Undocumented work isn't finished. Update the docs **in the same pull request** as the change, never "later".

- **Architecture, tooling, security or configuration changed?** Update the page in `_docs/` that describes it (`_docs/architecture/overview.md` for how the app works). That covers routing, rendering, the proxy and headers, environment variables, layouts, the theme, state, dependencies, linting, testing, hooks and CI.
- **Made a decision someone could later ask "why?" about** (a new dependency, pattern, library or convention)? Add an ADR in `_docs/adr/`. Never rewrite an accepted ADR; supersede it with a new one.
- **Changed a rule or workflow?** Update this file, plus README, CONTRIBUTING or SECURITY where they describe it.
- **Changed a component?** Update its stories so Storybook shows every variant, state and prop that exists now; the docs page is generated from the stories and types. New components need a story and a test (`pnpm check:stories`).
- **New environment variable?** Document it in `.env.example` (what it's for, public or server-only, an example value) and read it with a safe default.
- **Built a screen?** Replace its placeholder, keep the D##/M## comment, and resolve or record any open decision from `_docs/design/HANDOFF.md`.

`pnpm check:docs` (and the required `docs` check in CI) fails a pull request that changes architecture without touching the docs, or changes a component without its story. If a change truly needs no docs, say why in the PR description with a line such as `Docs: not needed — only renames a local variable` (or `Stories: not needed — …`); reviewers check that reason.

## 10. Before you say a task is done

1. `pnpm validate` passes: format, lint, typecheck, check:tokens, check:comments, check:stories, test (including the Storybook stories) and build.
2. `pnpm check:docs` passes: the docs and stories describe what you changed (section 9).
3. The screen matches its D## and M## frames in Figma at 1440px and 390px.
4. Every new or changed component has an up-to-date story and test.
5. The work is on a branch, with a PR into `dev` open as described in section 8.
